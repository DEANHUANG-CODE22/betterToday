# 早上六点四十，一个决定

**一个训练决策产品的需求文档（对外版）**

> 这份文档写给两类人：想看产品怎么被想出来的人，和想知道「健康数据到底能不能变成行动」的人。
> **最后更新：2026-11-07，对应内部版 v0.6。** 这一天改的是信息架构（三栏、起床先看昨夜、剂量在训练前看）。规则和参数没有改。
> 所有数字都来自一个真实账号的三个月数据；身份信息已去掉，数值保留。

---

## 摘要

大多数健康产品在解决「怎么把数据看清楚」，这个产品在解决「怎么把决定做出来」。

它只有一句话：**早上打开一次，就知道今天练不练、练什么、凭什么。**

做下来有三条反直觉的结论，也是这份文档的主线：

1. **恢复分不是成绩单，是许可证。** 用户不需要知道「73 分是什么水平」，只需要知道「73 分允许我今天做什么」。
2. **休息得越久，所有指标越显示「你状态极佳」——而那恰恰是最危险的时候。**
3. **它成功的标志，是用户越来越少打开它。**

---

## 1. 问题不是没有数据，是没有决定

一个有系统训练习惯的人，早上醒来面对的真实问题只有一个：

> 今天该不该上强度？

为了回答它，他要在手表 App 里做这些事：看恢复分 → 翻到睡眠 → 再看 HRV → 切到训练负荷 → 回忆昨天练了什么 → 最后凭感觉拍一个。

数据全都在。**但决定没有因此变快，反而变慢了。**

这不是信息不足的问题，是**信息没有被压缩成判断**的问题。一个用户在看到「HRV 高于基线 9%」时，脑子里要额外跑三步：9% 算多吗？这跟我昨天练的有关系吗？所以我今天该干什么？

产品要做的，是把这三步替用户跑完。

### 1.1 一个具体的失败

真实数据里最典型的场景是这样的：连续几天睡眠不足、训练偏密，某天早上他跑了一小段就停了，接下来 **16 天没有训练**——受伤了。

事后回看那几天，数据并不难看：睡眠够、HRV 在基线内、负荷为零。**每一条都指向「状态极佳」。**

这个案例后来成了整份文档里最重要的一节（见 §5.3）。

## 2. 用户与场景

### 2.1 谁

有系统训练习惯的耐力运动爱好者——马拉松、越野、铁三。每周训练 4 到 7 次，能看懂 HRV、静息心率、训练负荷、阈值配速这些词，但不想每天早上翻好几层页面把它们拼起来。

这个版本只服务一个人：产品作者本人。不做多账户、不做合规、不打算上架。

### 2.2 不服务谁

- 只看步数、睡眠分数的轻度用户——手表官方 App 对他们够用。
- 管理多个学员的教练——那是训练营系统的活。
- **把「逛数据」当成主要目的的人。** 查看数据是手段，做决定才是目的。

> 这里改过两次。第一次删掉「不服务想逛数据的人」。2026-11-07 再定：白天按日期看步数、静息心率和压力，是正式的一栏。这些数不单独改今天的剂量。

### 2.3 一天里的四个场景

场景不是页面。四件事落在三块内容上。

| 场景 | 要办完的事 | 落在 |
| --- | --- | --- |
| 起床后 | 昨夜睡眠时长、夜间 HRV、最新恢复，以及每项的记录时间 | 睡眠与恢复（打开就是这里） |
| 白天 | 按日期看步数、静息心率、压力，并看到缺了什么 | 日常健康 |
| 训练前 | 当天建议和依据。缺了关键输入，就写明缺什么 | 运动 |
| 运动后 | 这一次的时长、距离、配速或速度、心率、已有分段；对照当天建议 | 运动 |

训练前和运动后共用「运动」。没有当天记录时，上面是建议。有了记录，上面先是这一次。对照的是当天建议，不是一份训练计划。

休息日不进「运动」，就看不到建议。这个取舍先这样。

> 同一个问题不跨两块内容。早期版本把「能不能上强度」和「练什么」拆到两个屏幕，一次决定要打开两次。建议现在只在「运动」里。

## 3. 定位

### 3.1 一句话

**把身体数据收成今天这一练的剂量。起床先看昨夜，剂量在训练前看。**

### 3.2 它不是什么

边界比定义更重要，这四条是刻在产品墙上的：

1. **不是仪表盘。** 一屏十几个指标，本质是把解释成本推回给用户——那是产品没做出判断的证据。
2. **不是打卡机。** 连续打卡、勋章、排行榜是健身和习惯类产品的语言。身体不是待办事项。
3. **不是医生。** 不做诊断、不承诺疗效。越界一次，失信永久。
4. **不是内容平台。** 用健康科普填日活，等于承认核心功能没价值。

### 3.3 低存在感，高在场感

这类产品的全部设计难度，可以压进一个 2×2：

|  | 数据不连续、不记得你 | 长期记忆、关键时刻都在 |
| --- | --- | --- |
| **天天推送、要你打开** | 大多数健康 App 的现状：又烦又没用 | 早期健身 App：有用，但撑不过三个月 |
| **不打扰、不索取注意力** | 买了不戴的硬件：钱花了，关系没建立 | **唯一可持续的位置** |

**存在感要低（别打扰我），在场感要高（你一直在，且记得我）。**

这两件事不但不冲突，还互为前提：正因为平时不烦你，关键时刻那一次才有分量。

### 3.4 三个入口怎么分工

后来加了一个「数据」入口。加之前对比了 Oura、WHOOP、Garmin 三家：

| | 首页 | 数据入口 | 长期 |
| --- | --- | --- | --- |
| Oura | Today + 一排可自定义的 Shortcuts（最少 3 个） | Vitals（分组卡片） | My Health |
| WHOOP | Sleep / Recovery / Strain 三个表盘 | Health | 各模块内 |
| Garmin | Essentials（用户自选，最多 4 个指标） | dashboard 分区 | Reports |

三家的共同点很清楚：**首页只放 3–4 个精选，完整数据另给一个入口。**
没有一家把几十个指标平铺在首页。

2026-11-07 起，底栏按一天的顺序排，默认最左：

| 入口 | 回答 | 形态 |
| --- | --- | --- |
| 睡眠与恢复 | 昨夜怎么样，各是什么时候记下的 | 睡眠时长、夜间 HRV、恢复。缺的单独写 |
| 日常健康 | 某一天的日常，缺了什么 | 按日期看步数、静息心率、压力 |
| 运动 | 练前的剂量，练后的这一次 | 没有记录时上面是建议；有记录时上面是这一次和对照 |

本周量和运动能力不在底栏里，收在「运动」下面。

**同一个数字可以出现两处，角色必须不同。** 日常健康按天翻。建议依据只回答今天缺不缺、偏不偏。

## 4. 设计原则

1. **结论先行。** 每屏顶部先给一句话结论，再展开数字。
2. **和自己比。** 所有指标默认对个人 7 日 / 28 日基线，不对人群。
3. **可解释。** 每条建议都列出依据；依据互相矛盾时，把矛盾说出来。
4. **建议在一屏里看完。** 人在「运动」里、当天还没有记录时，判断和依据不靠滚进别的栏目。打开 App 的第一屏是昨夜。
5. **缺数据就闭嘴。** 样本不足、字段缺失、规则冲突时，输出「不确定」并说明原因。宁可说不知道，不可猜。
6. **断言分级。** 一次是事实，三次是模式，五次才是你的特点。断言强度永远不超过证据强度。
7. **沉默即确认。** 符合预期时不说话。没消息就是好消息，这句话只在周报里说一次。
8. **教练语气，不是裁判语气。** 同一句「今天别练」，可以给判决，也可以给出路。

## 5. 核心机制

### 5.1 剂量在「运动」里说完

下面这张是训练前、「运动」上方还没有当天记录时的样子。打开 App 的第一屏不是它，是昨夜的睡眠、HRV 和恢复。当天有了记录，这一次和对照放在建议前面。

```
┌────────────────────────────────────────────┐
│ ● 一切正常 · 恢复 73 中上 · 静息 46          │
├────────────────────────────────────────────┤
│ 今天：可以上强度                             │
│ 阈值跑 40min｜Z4｜心率 168–175               │
│ 恢复 73 · 中上 —— 够一次强度课，不够连续两天  │
│ ──────────────────────────────────────────  │
│ 为什么                                       │
│  昨晚恢复得比平时好 —— HRV 比常态高 9%，有余量 │
│  睡够了 —— 7 小时 42 分，撑得住一次强度课      │
│  疲劳没欠账 —— 负荷比 −6，这周只上过 1 次强度  │
│  昨天的账已经平了 —— 说恢复跑，你跑了 32min Z2 │
│ ──────────────────────────────────────────  │
│ [ 做完了 ]   [ 改一下 ]   [ 今天不练 ]        │
└────────────────────────────────────────────┘
```

这块要一次看完判断、处方和依据。睡眠、HRV、恢复的原件在「睡眠与恢复」，每项带自己的记录时间。依据可以引用它们，并写明缺了什么。

当天有记录之后，上面换成三行：建议是什么、这一次做了什么、接下来怎么办。对照的是当天建议。

依据那四行是推理，不是把数据库再念一遍。见 §5.6。

### 5.2 恢复分：从「分数」到「许可」

最初的设计是显示「恢复 73」。问题很明显：73 分是什么水平？好还是不好？跟谁比？

一个分数要有意义，必须有参照系。而参照系有四种：

| 参照系 | 例子 | 用不用 |
| --- | --- | --- |
| 绝对档位 | 优 / 良 / 中 / 差 | ✅ |
| 相对基线 | 比你的 28 日均值高 9% | ✅ |
| 社会比较 | 同龄人里排前 30% | ❌ 永远不用，只制造焦虑 |
| **行动参照** | **这个分数允许我今天做什么** | ✅ **最关键的一种** |

信用卡评分是最成熟的先例：没人真的懂 742 分是怎么算的，但所有人都懂「很好，能拿到最低利率」。

**所以恢复值永远以三件套出现：数字 · 档位 · 许可。**

> ✅ `恢复 73 · 中上 —— 够一次强度课，不够连续两天`
> ❌ `恢复 73`（裸数字）
> ❌ `恢复 73%，状态中等偏上`（有档位没许可，等于没说）

**健康评分的本质不是成绩单，是许可证。**

### 5.3 回归期：数据分不清「休息够了」和「伤好了」

这是整个项目里最有价值的一段，因为它推翻了一个看起来很合理的规则设计。

#### 规则的原始形态

建议引擎的判断链大概是这样：恢复好不好？负荷高不高？最近有没有上强度？只要都合格，就建议上强度课。

这套逻辑在连续训练期工作得很好。**但它有一个结构性缺陷：休息越久，每一个条件都会变得更"好"。**

| 判断输入 | 休息 9 天之后 | 规则怎么读 |
| --- | --- | --- |
| 恢复分 | 睡满 9 小时，HRV 在基线内 | 充足 ✓ |
| 短期/长期负荷比 | 近 7 天负荷为零 | 远低于风险线，安全 ✓ |
| 疲劳状态值 | 疲劳衰减到零，体能还在 | 正值，可以练 ✓ |
| 近 7 天强度课 | 0 次 | 可以上强度 ✓ |
| 距上次强度课 | 9 天 | 可以上强度 ✓ |
| 异常信号 | 无 | 一切正常 ✓ |

六条全绿，引擎输出：**「强度课，Z4–Z5」。** 而那是在受伤之后第 9 天。

#### 真实回放的结果

用真实账号数据把三个月的每一天都跑了一遍，结果是这样：

| 距上次训练 | 当晚睡眠 | 当晚 HRV | 引擎输出 |
| --- | --- | --- | --- |
| 3 天 | 6h42m | 67 | **可以上强度** |
| 6 天 | 6h48m | 74 | **可以上强度** |
| 7 天 | 7h45m | 66 | **可以上强度** |
| **9 天** | **9h01m** | **63** | **可以上强度** |
| 14 天 | 无数据 | 无数据 | **可以上强度** |
| 15 天 | 无数据 | 无数据 | **可以上强度** |

**在一段 16 天的伤退期里，它有 6 天建议上强度。**

注意这些天的共同点：**不是数据异常，而是数据太好。** 睡够了、HRV 在基线内、负荷为零——所有规则都指向「状态极佳」。

#### 一个差点被掩盖的细节

更有意思的是复训第一天。那天引擎输出的是「休息」，看起来完全正确。

但那是**巧合**：前一晚只睡了 4 小时 56 分、HRV 掉到 41，恢复分直接掉到 30。

**换一个睡得好的早晨，同一个伤病状态就会得到「上强度」。** 也就是说，这个系统的结论取决于当晚睡眠——一个跟伤病毫无关系的随机变量。

#### 修法：不是一个阈值，是一个时序状态

调参数救不了这个缺陷，因为它不是「阈值太松」，而是**缺一个状态**：系统分不清「休息够了」和「伤好了」。

于是加了一个优先级最高的状态：

**回归期多长，不能靠猜，得问一次。** 中断超过 7 天，系统只问一个问题：「大概多久能恢复？」

| 回答 | 回归期 |
| --- | --- |
| 没受伤，只是主动休息 | 10 天 |
| 轻伤，3 天内能好 | 10 天 |
| 1–2 周 | 14 天 |
| 3–4 周 | 21 天 |
| 更久（骨性、术后等） | **42 天** |
| 没回答 | 21 天（保守默认） |

> 这里原来只有「伤病 21 天 / 主动休息 10 天」两档。改的原因是：**「伤病」是一个桶，感冒、跟腱炎、骨应力性损伤都装在里面**——用一个 21 天打天下，等于把最严重的伤按最轻的处理，而这恰恰是这套规则要防的那类事故。

| 项 | 规则 |
| --- | --- |
| 触发 | 距上次训练 ≥ 7 天（还在中断中，或刚回来仍在回归期） |
| 起始量 | 中断前 4 周周均的 **50%**（伤病）/ 70%（主动休息） |
| 强度上限 | 伤病类 Z2 / 主动休息 Z3；期间**禁止强度课** |
| 周增幅 | ≤ 15% |
| 负荷比、疲劳值 | **不参与判断**（分母失真，读数无意义） |
| 置信度 | 恒为「低」，文案必须写「回归期第 N 天」 |
| 退出 A（量回来了） | 天数 > 档位，**且连续两个 7 天窗口**都回到中断前的 **65%** |
| 退出 B（无异常放行） | 天数 > 档位 **+7**，且近 14 天无异常信号，且近 7 天练了 **≥3 次**，且量 ≥ **50%** |
| 兜底 C | 天数 > 档位 ×2，强制放行，防止永远卡住 |

**退出条件改过三次，每次都是被真实数据打回来的。**

第一版：「连续 14 天有训练 + 量恢复 80%」。实现时发现「连续 14 天」会被任何一个休息日清零，太脆。

第二版：「天数够 + 近 7 天量 ≥ 80%」。单一 7 天窗口仍然会被一周的偶然波动影响——真实数据里，回归期第 22 天他一次还只跑 3 公里，周训练量不到中断前的三成，那时「出关」等于放任加量。

第三版：两个 7 天窗口都要达标。这一版上线后仍嫌保守——他复训三周、已经能跑 5 公里，却因为差几个百分点继续被按「回归期第 28 天」管着。

第四版就是现在的三条出口：比例降到 **65%**，另加一条「**无异常放行**」——过了档位再多等一周、没有异常信号、而且确实在练，就放行。

为什么放行门槛写成「档位 +7 天」而不是固定的 28 天？因为写死会让 42 天档（骨性、术后）在第 29 天就出关，等于把最重的伤按最轻的处理。

为什么还要「近 7 天 ≥3 次」？因为**躺了一个月的人也没有异常信号**——不加这条，放行等于什么都没防。

第三版是现在这个：**连续两个 7 天窗口都要达标**。有人会问为什么不用 28 天滚动窗口——因为回归期本身只有 21 天，28 天窗口在期内数学上不可能满足，只会把所有人推到 2 倍兜底。两个 7 天窗口是这两者之间唯一可用的档。

修完之后，同一段数据跑出来是这样：

```
09-29 起连续 27 天全部是「回归期」，
每一屏都写着第几天、今天多少分钟、这周上限多少。
```

伤退期 + 复训期一共 53 天，只剩 1 天还在建议上强度——那是一次中断 3 天，属于正常的训练间隔，产品没有任何依据判断他受伤了。

### 5.4 置信度：缺数据就闭嘴

这个功能的第一版有个隐蔽的漏洞：判断置信度时，它只检查「近 7 天有几天睡眠数据」，**从来不检查今天这一晚**。

结果：连续五个晚上完全没有睡眠记录，引擎照样给出「高置信度」的强度课建议。

修法很直接：

| 情况 | 置信度 | 建议 |
| --- | --- | --- |
| 数据齐全 | 高 | 正常判断 |
| 今夜有睡眠、无 HRV | 中 | 仍可给强度课，不**过度**降级 |
| 今夜无睡眠 | **低** | **不出强度课**，文案说明缺的是昨夜睡眠 |
| 刚授权、无历史 | — | 「先戴几天，我需要 7 天才能判断」 |

第三行和第四行是同一个原则：**宁可说不知道，不可猜。**

**但「不知道」不止一种。** 比缺数据更隐蔽的是「数据在，但不可信」：

- 手表记录会有 GPS 漂移、心率带脱落、中途断连。这些记录算出来的训练负荷是错的，而负荷比、体能、疲劳**全都建在它上面**。一条离谱的记录会污染分母，然后被规则放大成一个决定。
- 所以加了数据质量闸门：时长不足 2 分钟、心率超出生理范围、配速不可能的记录，**不进负荷计算**；近 28 天数据不全的占比超过 30%，置信度直接降「低」。
- 但闸门的尺子要按运动分：跑步 3:00–15:00 /km，走路和徒步 1:00–12:00 /km，骑车游泳不判配速（40 km/h 是正常的）。**用跑步的尺子量徒步，会把一次 3 小时、1.9 km/h 的徒步判成坏记录删掉**——删掉之后 28 天的慢性负荷变小，负荷比虚高到 1.8，连续几天输出「今天别跑」。这条是上线后被真实数据抓出来的。
- **「缺一个字段」不等于「记录有问题」**：列表接口不返回单次负荷，如果把它当成坏记录，整批数据会被判可疑，回归期会从两个月前算起。

**还有一类情况：依据互相打架。** 比如睡得很少但 HRV 不差；比如压力在偏离但 HRV 仍在基线内。这时不是「没数据」，是「数据之间矛盾」：

| 矛盾条数 | 输出 |
| --- | --- |
| 1 条 | 最高「中」；本要给强度课的话，改成按有氧走 |
| **2 条以上** | **强制「低」**，并在文案里把矛盾原样写出来 |

> 写这一段时我先加了一条看起来合理的规则——「恢复不错但负荷比偏高」也算冲突。测试直接把它打回：负荷比 > 1.3 时疲劳值必然低于 −10，而低于 −10 本来就会挡掉强度课，两条规则互斥。
> **凡是加不进可达分支的规则，都是自欺欺人。** 这条被删掉了。

顺带一个细节：最小样本量也要管。HRV 基线不足 7 天，就显示「基线建立中 3/7」；恢复值缺失就直接显示「数据不足」，**不估算、不合成**。一个 3 天的「恢复 92%」比没有更糟。

### 5.5 双闭环：行为可以被动获得，意图只能主动获得

建议发出之后，怎么知道用户到底练了没有？这件事有两种反馈：

|  | 显式（点按钮） | 隐式（运动记录比对） |
| --- | --- | --- |
| 测什么 | **意图**：我本来想练什么、为什么改了 | **行为与结果**：实际练了什么 |
| 成本 | 用户一次点击 | **0**（记录本来就在同步） |
| 偏差 | 自报偏差，问多了会糊弄 | 无自报偏差，但有歧义 |
| 频率 | 尽量少 | 每次都采 |

**核心分工：行为可以被动获得，意图只能主动获得。** 所以不是「被动替代主动」，而是各管一半。

判断结果分三档：**一致**、**等价**、**偏离**。

> **现在的实现只做了一半，说清楚**：已进代码的是「强度档 + 时长」——档对上、时长在 ±20% 内算一致，量差一档算等价。还没做的是「平均心率落在建议区间 ±5 bpm」（处方里只有文字区间，没有数值）和「等价看训练负荷 ±30%」（处方本身没有可比的负荷值）。所以现在这一档比设计写的宽，阈值也没有校准过。

「等价」这一档必须给出可执行的判据，否则它就是一个模糊地带：

| 档 | 判据 |
| --- | --- |
| 一致 | 类型相符，时长在建议的 ±20% 内，平均心率落在建议区间 ±5 bpm |
| 等价 | 类型不同，但**训练负荷在建议的 ±30% 内**，且主强度落在同一心率区间 |
| 偏离 | 以上都不满足，或没执行 |

用「训练负荷」而不是「时长」做等价换算，是因为 45 分钟跑步和 60 分钟骑车在时间上不等价、在生理代价上可能等价。

偏离后只问一次：

> 「昨天建议休息，你上了强度 —— 是因为？」
> 状态其实不错 / 有计划在身 / 就是想跑 / 别问了

选「别问了」，这类问题**冻结 90 天**不再问，设置页留一个重新开启的开关。**同一类问题 14 天内最多问一次**——问多了用户会开始糊弄，你的地面真值就被污染了。

> 原来写的是「永久不再问」。改掉的理由很直接：一次烦躁就把这一类真值永久丢掉，闭环直接断裂。但也不能立刻再问——那叫不听用户说话。90 天是个折中。

还有一条容易被忽略的：**「今天没练」是有歧义的。** 可能是主动休息、可能是忘了戴表、可能是受伤。三者的含义完全相反。所以要先看有没有全天心率数据，区分「戴了但没练」和「压根没戴」；分不出来的情况，不猜。

### 5.6 表达：禁止裸数字

这一节看起来像文案要求，其实是产品要求。

早期的「为什么」里长这样：

> · HRV 58ms，比 28 日均值高 9%
> · 睡眠 7h42m，够
> · TSB −6，近 7 天只上过 1 次强度

用户点开「为什么」，看到的是**一个数据库**，而不是**一个理由**。

改成这样就对了：

> · 昨晚恢复得比平时好 —— HRV 比你的常态高 9%，身体还有余量
> · 睡够了 —— 7 小时 42 分，撑得住一次强度课
> · 疲劳没欠账 —— 负荷比 −6，这周只上过 1 次强度

规律很清楚：**人话在前，数字在后；破折号后面才是证据。** 数字从主角降级为佐证。

四条硬规则：

1. 人话结论在前，**不许以指标名开头**。
2. 每条必须包含「**对今天的含义**」，停在生理含义等于没说。
3. **禁止裸数字**，任何数字都要带参照（比基线 / 比常态 / 比上次 / 比建议）。
4. 一段最多 4 条依据。超过 4 条，说明你在倒数据，不是在解释。

配套的还有语气。同一句「建议休息」：

| 场景 | ❌ 裁判 | ✅ 教练 |
| --- | --- | --- |
| 该休息 | 你今天状态差，别练了 | 今天别上强度。想动就 20 分钟散步，别超过 130 |
| 数据矛盾 | HRV 良好，建议强度课 | HRV 不错，但只睡了 5h34m——这条我拿不准，建议按有氧走 |
| 想硬练 | 不建议这样训练 | 想练也行，把强度压在 Z2，别再顶阈值 |
| 偏离计划 | 你没有按计划训练 | 昨天说休息，你上了强度——这次不追，明天看恢复再说 |

三条 do：给动作、给区间、给上限；说不确定时要说清为什么；允许用户不听，并给出「听了但打折」的版本。

三条 don't：不评判人格；不给无法执行的判断（「你的睡眠质量差」——然后呢？）；不用感叹号和 emoji 制造情绪。

## 6. 指标口径

| 指标 | 定义 | 基线 / 阈值 |
| --- | --- | --- |
| HRV | 夜间 HRV（ms） | 7 日 / 28 日均值；偏离 ±7% 视为显著 |
| 静息心率 | 当日最低稳定心率 | 比 28 日均值高 ≥ 5 bpm 视为偏高 |
| 睡眠时长 | 入睡到醒来，扣除清醒 | **低于自身 28 天中位数 30 分钟以上**视为不足；< 5h 为严重 |
| 恢复 | 设备提供的恢复百分比，**原样使用**，不合成 | 分四档：充足 / 中上 / 偏低 / 不足 |
| 训练负荷 | 单次训练负荷 | 每日求和 |
| 急性/慢性负荷比 | 7 日负荷均值 ÷ 28 日负荷均值 | 0.8–1.3 安全，>1.5 高风险 |
| 疲劳状态值 | 体能 − 疲劳 | 低于 −30 视为累积明显 |

**基线是滚动的。** 所有「个人基线」都取最近 28 天（含当天）的滑动窗口，不是固定初始化的值。这样体能长期变化、体重变化会自然反映进基线。

代价是：**结构性变化会被当成异常。** 如果一个月的训练量整体上了一个台阶，前 28 天里新旧两段混在一起，基线会被拉平，短期异常检测会迟钝。这也是为什么所有判据都配了相对阈值，而不是只看单一指标——单纯比基线，遇到长期漂移一定会误判。

**睡眠阈值这里修正过一次，值得记。** 最初用的是绝对阈值「低于 6.5 小时算不足」。真实数据显示，这个账号在三个月里分别有 **68% / 70% / 66%** 的日子低于 6.5 小时。

也就是说，按旧口径，产品一年有三分之二的时间在报警。

**这不是阈值偏严，这是可以提前算出来的报警疲劳**——用户会在两周内学会无视它，然后连真的警报一起无视。后来改成相对自身基线（低于自己 28 天中位数 30 分钟），并加了一条验收：告警率必须落在 15%–30% 之间。

## 7. 触达：两条通知，一条规则

产品的主体其实不在 App 里，在那两条推送里。

| 通知 | 时机 | 触发条件 |
| --- | --- | --- |
| 早间判断 | 默认 09:30，可配置 | 有建议，且不是「不确定」 |
| 训练后结算 | 记录同步完成 10 分钟内 | 有偏离，或有一句明确的恢复动作 |
| 模式提醒 | 连续 2 天同向偏离 | 且证据已够形成「模式」 |
| 周报 | 周日 20:00 | 趋势 + 沉默周的确认 |

四条硬规则：

1. **每日上限 2 条。**
2. **夜间静默**（22:00–07:00）。
3. **过时不补发。** 结算通知落在静默期就直接丢弃——即时反馈过期就是噪音，第二天早上补发「你昨天那次跑得对不对」毫无价值。
4. **符合预期不推。**

还有一条防报警疲劳的机制：「与预期不符」的阈值必须**宽于**「异常」阈值。HRV 异常是 ±7%，偏离要 ±10% 且连续 2 天。否则会天天报警，然后被无视。

**「同向偏离」也要定义清楚**，否则「连续 2 天同向偏离」是一句空话：连续两天的偏离**方向一致**才算——都超量，或都不足。一天超量一天不足算两次独立偏离，不触发模式提醒。

**周报的三条红线**（内容待定，规矩先立）：

1. **结论先行**：开头一句判断，不是开头一堆图。
2. **禁止裸数字**：所有数字带参照。
3. **沉默即确认**：没异常就不写「本周一切正常」这种凑字，单周可以不发。

> 周报是最容易做回「数据周报」的地方。违反任意一条，就等于把产品在做的「不逛数据」又还回去了。

## 8. 怎么判断它成了

不是 DAU，不是打开次数。五条：

1. 连续 14 天，训练前在「运动」里 10 秒内看完「练不练」；依据里要的数不用去官方 App 里查。（打开 App 先看到的是昨夜。同步要打开官方 App，那是链路前提，不算验收项。）
2. 至少 3 次，建议与我原本意图不同，事后我认为它对。
3. 至少 3 次，我**没有打开 App** 就收到了结论。
4. 打开即见昨夜睡眠时长、夜间 HRV、最新恢复，以及各自的记录时间。缺的写缺。「运动」里还没有当天记录时，判断、处方和依据在同一屏。
5. 随机抽 10 条文案：0 条命令句、0 条人格评判；10 条依据里 0 条以指标名开头。

> 原来还有第六条「连续 14 天推送总数 ≤ 28 条，且至少 3 天完全无推送」。它**暂缓**：推送策略还没做，现在验它是空的。等触达做完再启用——但「沉默即确认」这条原则保留：符合预期的那一次不推。

**这五条的可验证性不一样，要分开看：**

| 类型 | 条目 | 怎么验 |
| --- | --- | --- |
| 可自动化 | 首屏信息完整、文案质量、依据不以指标名开头 | 有测试或可抽查清单 |
| 需真机两周 | 10 秒决策、建议与意图冲突时我认可、无 App 收到结论 | 每天一行记录：日期 / 是否 10 秒内决定 / 有无改变原计划 |

真机那部分没有记录表就等于没有验收——三周后只会剩下「感觉还行」这四个字。

还有一个反向指标：**「用户主动放弃查看的天数」——这个数越高越好。** 用户少看我们，说明信任建立了、焦虑消退了、能力转移了。

## 9. 边界与还没解决的问题

**能保证的**：训练前，「练不练」能在「运动」里 10 秒内看完，并且有据可查。起床先看到的是昨夜，不是这句剂量。

**不能保证的**：

- **它预测不了受伤。** 真实数据里那次伤退，前一周的负荷在 10–30 公里之间正常波动，还有两周降了载，没有负荷激增。数据里找不到原因。**这个产品拦不住受伤，它只能保证你回来的时候不被自己害第二次。**
- **它替代不了医生**，也不做任何疗效承诺。
- 恢复值的四档边界目前是默认值，**需要先用本人 60 天数据按分位点校准**才能冻结。没校准之前，只显示数字、不出档位和许可语。
- 被动闭环依赖运动记录同步，漏同步的日子只能当「不知道」处理。

**开放的三个问题**：

1. 如果一款健康产品真的帮用户养成了习惯，它是否反而降低了对产品的依赖？这是订阅制与用户价值之间真实的张力，目前没有答案。
2. 「一致性判断」的等价档（换运动方式但负荷相当）需要多少容差才算合理，还没有数据支撑。
3. 周报要不要做、做成什么样，取决于前两条能不能站住。

### 9.1 接下来做什么（以及为什么是这个顺序）

| 顺序 | 要做的事 | 解决什么 |
| --- | --- | --- |
| 1 | **恢复分校准** | 现在的四档边界是临时值，要先用本人 60 天的分布定出来，否则「许可」是猜的 |
| 2 | **隐式闭环** | 现在只知道你点了什么，不知道你实际练了什么——而运动记录本来就在同步，这一步几乎免费 |
| 3 | **语气规则** | 把「教练不是裁判」变成可检查的清单，而不是一份没人看的风格指南 |
| 4 | **通知策略** | 训练后结算、每日上限、静默、过时不补发 |

**顺序不是按难度排的，是按「说得对不对」和「说得舒不舒服」排的。** 前两件决定答案可不可信，后两件决定它烦不烦人。反过来做，就会得到一个很体贴但没什么用的产品。

三栏（睡眠与恢复、日常健康、运动）已经做进当前安装包。下面四件仍是之后要做的。

## 附录 A：一次自我推翻

这份文档里 §5.3 的结论，第一次是**错的**。

我先凭推演说：复训第一天（伤退后第 16 天）系统会建议上强度课。这个推论很顺——休息越久，所有指标越像「状态极佳」。

然后我真的把代码跑了一遍。那天的输出是**「休息」**。

原因：前一晚只睡了 4 小时 56 分，HRV 掉到 41，恢复分跌到 30。**规则偶然地对了。**

所以：

- **缺陷是真的**，但我说错了它会在哪一天发作。
- 真正的问题不是我推论的方向错，而是**我拿推论当结论**。
- 这次之后就做了一个决定：**把那一整天的真实数据固化成一条自动化测试**。以后谁改规则，把这天又判回「上强度」，测试会立刻变红。

现在这个项目里有一条约定：**改建议规则前后，必须跑一次全周期回放。** 一次回放会把三个月的每一天都过一遍，输出每天的建议；和基线对比，就知道改动影响了哪些日子。

**结论可以错，但要能被数据当场推翻。** 这大概是这个产品里唯一一条适用于所有环节的原则。

### C.2 一条规则的骨架

回归期判断的核心（节选）。它不是阈值，是一个状态机：

```ts
// 还在中断里，没回来
if (gapNow >= 7) return { phase: 'gap', daysIn: gapNow, ... };

// 已经回来：从最近一次训练往回找，这段训练块的起点在哪
let i = dates.length - 1;
while (i > 0 && daysBetween(dates[i - 1], dates[i]) < 7) i -= 1;
if (i === 0) return undefined;          // 从来没中断过，不在回归期

const daysIn = daysBetween(start, date) + 1;

// 天数够、**而且量真的回来了**，才算结束
if (daysIn > limit && volumeBack) return undefined;
```

### C.5 还没验证的

诚实起见，这些不算数：

- **两周真机验收还没跑。** §8 的 5 条标准里，打包前能验的只有 3 条。
- **结算的判据没校准。** ±20% / ±50% 是拍的，不是从你的记录里长出来的；而且「平均心率落在建议区间」还没比。
- **恢复值的四档边界是默认值，未校准。** 要用本人 60 天数据按分位点定完才启用档位和许可语。
- **界面截图待补。** 回归期卡片还没装到设备上，现有截图是上一版的。
- **样本量是 1，只有三个月。** 所有统计都只能算提示，不能算结论。
- **本文所有参数只在这一个账号上验证过。** 21/42 天的回归期、50%/70% 的起始量、65% 的出关线、±30% 的等价容差，都来自通用康复与训练常识，不是从数据里拟合出来的——它们的风险不是「过拟合到这个人」，而是**「可能对这个人也不准，只是还没验证过」**。搬到别的用户身上，需要各自重新校准。
